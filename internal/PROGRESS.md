### 2026-10-04 — P0-6 done: fixed first-run setup failure (working tree, uncommitted — no branch created)
- **Reported symptom:** user hit "Could not install the OryCMS database schema. Check the database connection." when running first-run setup.
- **Diagnosis:** the message is misleading. Confirmed via a temporary, since-deleted diagnostic script (not committed, not left in the repo) that the configured database connects fine (reachable, authenticated, Postgres 18 on Neon) and 9 of 11 core tables were already installed from a prior run. The real failure was Postgres rejecting the generated DDL for exactly two tables — `orycms_tokens` and `orycms_audit_logs` — with `column "createdAt" specified more than once`. `app/api/orycms/auth/setup/route.ts` returns a generic, hardcoded message on any install failure and never surfaces `bootstrap.install.failed`'s actual per-migration error — that's a separate, smaller follow-up worth its own task if this kind of failure recurs (not logged as a new row since it's a minor UX/debuggability gap, not a correctness bug — flagging here instead).
- **Root cause:** `orycms/core/core.collections.ts`'s `oryTokens` and `oryAuditLogs` collections each explicitly declared a `createdAt` field in their `fields` array, while `orycms/mapper/collection.mapper.ts` also unconditionally auto-injects a system `createdAt` timestamp column unless a collection sets `timestamps.enabled: false` (neither collection did). Every other one of the 11 core collections relies on the auto-injected column and does not declare `createdAt` itself — these two were the only outliers.
- **Fix:** removed the redundant explicit `createdAt` field from both collections, in both `orycms/core/core.collections.ts` and its byte-identical counterpart `packages/core/src/core/core.collections.ts`. Updated the one test asserting the now-removed field (`"has createdAt as required date-with-time field"`) in both `orycms/core/__tests__/core.collections.test.ts` and `packages/core/src/core/__tests__/core.collections.test.ts` — removed rather than rewritten, since no other core collection has an equivalent test (the field is a standard system column, not something these tests otherwise probe) and the two test files are kept byte-identical by convention.
- **Verification against a real database:** re-ran the actual `installOryCMSCoreSchema` logic (via a temporary script, deleted after use) against the same Neon database used to reproduce the bug. Before the fix: `success: false, failed: [orycms_core_orycms_tokens, orycms_core_orycms_audit_logs]` with the exact reported-adjacent Postgres error. After the fix: `success: true, applied: [orycms_core_orycms_tokens, orycms_core_orycms_audit_logs], failed: []`.
- **Quality gate (actual output):**
  - Root: `npm run typecheck` — clean. `npm run lint` — 269 problems (267 errors, 2 warnings), unchanged baseline. `npm test` — 1330 passed, 4 failed (same 4 pre-existing unrelated binary-smoke failures; one fewer total test than before, matching the one test removed). `npm run build` — succeeds.
  - `packages/core`: `npm run typecheck` — clean. `npm test` — 772 passed, 0 failed (one fewer than its 773 baseline, same reason). `npm run build` — succeeds.
- **Not done:** the swallowed-error UX gap in `app/api/orycms/auth/setup/route.ts` (flagged above, not fixed — out of scope for this specific bug). No git write command was run.
- **Suggested branch name:** `fix/core-collections-duplicate-createdat`. **Suggested commit message:** `fix: remove duplicate createdAt field from core collections`.
