### U1-3 sub-tasks (planning done 2026-10-04 — see Log entry for the audit this is based on)

**Audit summary, before reading the table:** every route module except auth's 6 token-based flows (refresh/forgot-password/reset-password/activate/invite/accept-invite) **already has a line-count-matching, logically-equivalent port sitting in `packages/core/src/next/routes/*.ts`** — it's just not wired into `ORYCMS_ROUTES` and has barely been test-proven against the root's version. The old acceptance criteria (c) — "replace the root's 44 files with one catch-all route" — is **superseded by the 2026-10-04 Decision below** ("do not delete the 44 files in one step... thin wrapper... one module per task"); this table implements that decision literally, one route-module per sub-task. Decision also already made: `orycms/`'s versions of the 7 diverged engine files are authoritative (adopt into `packages/core/src`).

Shared mechanics every sub-task below follows:
1. If the module touches a diverged engine file not yet reconciled by U1-3.0, reconcile that file first (should already be done by U1-3.0 for all of them — flag it as a blocker if not).
2. Diff the root `app/api/orycms/**/route.ts` file(s) for the module against `packages/core/src/next/routes/<module>.ts` line-by-line. Where they differ (e.g. error-construction style), decide and document which behavior wins — default to the root's, since it's the one that's actually been run (same logic as the Decision on the 7 engine files), unless the root version has a known-open bug the core version happens to lack.
3. Add/extend `packages/core/src/next/__tests__/<module>.test.ts` to cover every route in the module (not just the one route `collections.test.ts` currently covers) — both as direct handler-level tests (existing pattern) and, once wired, dispatcher-level tests (`dispatcher.test.ts`'s pattern).
4. Wire the module's route array into `packages/core/src/next/routes/index.ts`'s `ORYCMS_ROUTES`. Update `mvp-surface.test.ts` (it currently hard-asserts the route list is auth-only — rename it or fold its assertions into a running "shipped surface" test that grows as each sub-task lands) and `dispatcher.test.ts`'s "does not ship advanced module routes" test (it will start failing for exactly this module, which is the proof the wiring worked).
5. Turn the corresponding root `app/api/orycms/**/route.ts` file(s) into thin wrappers: each exported `GET`/`POST`/etc. becomes a 2–4 line function that adapts `NextRequest` → the shared route's `OryCMSEndpoint` handler and returns its `Response`. (A small adapter helper — e.g. `toNextHandler(route: OryCMSRoute)` — is worth adding once in `packages/core/src/next/http.ts` or similar during U1-3.1 and reusing in every subsequent sub-task, rather than re-deriving it 9 times.) The root test for that module (where one exists) must still pass unmodified against the thin wrapper.
6. Quality gate (`AGENTS.md` §5) green for root and `packages/core` before marking `DONE`.
